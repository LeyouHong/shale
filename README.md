# shale

用 Go 从零实现的 **LSM Tree 存储引擎**，零第三方依赖。

> **shale**（页岩）是层状沉积岩，由沉积物一层层压实而成——正对应 LSM 的分层下渗与
> compaction 压实；同时延续 LevelDB / RocksDB / Pebble 的「石头」命名传统。

这是一个**学习向**的项目：目标是把 LSM 彻底吃透，代码可读性优先于性能。
完整的需求分析、设计决策和里程碑拆解见 **[DESIGN.md](DESIGN.md)**。

## 当前进度

| 里程碑 | 内容 | 状态 |
|---|---|---|
| **M0** | 骨架、Options、错误定义、**内部 key 编码**、**Batch 格式** | ✅ 完成 |
| **M1** | **跳表 + MemTable**（纯内存的 Put/Get/Delete） | ✅ 完成 |
| **M2** | **WAL + 崩溃恢复** | ✅ 完成 |
| **M3** | **SSTable 读写 + flush** | ✅ 完成 |
| **M4** | **Manifest + Version + 文件引用计数** | ✅ 完成 |
| **M5** | **Iterator + 多路归并** | ✅ 完成 |
| **M6** | **Compaction（简单全量合并）** | ✅ 完成 |
| **M7** | **Leveled Compaction + 分层** | ✅ 完成 |
| **M8** | **布隆过滤器 + Block Cache** | ✅ 完成 |
| **M9** | **后台 flush / compaction + 并发压测** | ✅ 完成 |

M0 刻意**先把两个最难改的决策落地**——内部 key 编码和 Batch 二进制格式。
它们是纯函数、不依赖存储，现在做掉，后面所有模块就不用返工。

M1 打通了读写路径。M2 加上 WAL，数据能活过重启——包括 `kill -9`。
M3 让数据落盘成 SSTable，内存和日志都不再无限增长。

M4 把元数据交给 Manifest：**目录里有什么文件不算数，Manifest 登记过的才生效**。
崩溃留下的孤儿文件因此会被自动忽略并清理。同时建立了 Version 的引用计数，
为 compaction 安全删文件打好地基。

M5 实现了多路归并迭代器，范围扫描可用。
M6 加上 compaction，**文件数终于能降下来**：

```
   M5（无 compaction）  598 个存活 key  →  136 个文件
   M6（有 compaction）  写入 3000 条    →  最终只剩 1 个文件
```

实测的几个数字：

| 观察 | 结果 |
|---|---|
| 50 个 key 反复写 100 轮（5000 条记录） | compaction 后只剩 **50 条** |
| 200 条数据 + 200 个墓碑，全量合并 | 磁盘占用降到 **0 字节** |
| 用户写入 1.1 MB | 磁盘实际写入 14.2 MB，**写放大 13.3 倍** |

最后一行值得单独说：**13.3 倍正好落在 LSM 理论上的 10~30 倍区间**。
这就是 LSM 的交易——前台写入极快，代价是后台持续重写数据。

M7 换成真正的 Leveled 分层：按 score 挑最拥挤的层、L1+ 轮转挑文件、
读路径改为二分定位。灌入 10 万条（21.6 MB）之后的实测分层：

```
   L0    2 个文件     97.9 KB / 256 KB   score 0.38
   L1    3 个文件    195.8 KB / 256 KB   score 0.76
   L2   39 个文件      2.5 MB / 2.5 MB   score 0.99
   L3  291 个文件     18.5 MB / 25.0 MB  score 0.74
```

**文件数 3 → 39 → 291，容量 256KB → 2.5MB → 25MB**，正好是 10 倍关系，
每层 score 都小于 1（compaction 跟得上）。

M8 加上布隆过滤器和块缓存。实测的假阳性率和理论值几乎完全吻合：

| 每 key 分配 | 实测假阳性 | 理论值 |
|---|---|---|
| 4 bit | 15.53% | 15.48% |
| 8 bit | 2.34% | 2.17% |
| **10 bit（默认）** | **0.84%** | **0.84%** |
| 16 bit | 0.04% | 0.05% |

查 10 万个「落在数据范围内但不存在」的 key：**过滤器挡下 99.09%**，
这些查询一次磁盘都没读。100 万个 key 直接存要 14.6 MB，过滤器只要 1.2 MB。

> 测这个有个坑：如果探测的 key 在字典序上完全落在已有数据之外，
> 更廉价的一层（L1+ 的二分边界检查）会先把它挡掉，
> **根本轮不到布隆过滤器**。所以测试统一用"写偶数、查奇数"。

M9 把 flush 和 compaction 挪到后台：MemTable 写满时只是**冻结换指针**，
落盘交给后台 goroutine，前台立刻继续。只有在后台严重跟不上时才踩刹车
（Write Stall）。

```
   写入 5000 条：最大单次延迟 20ms（M8 之前会因为同步刷盘出现几百毫秒尖峰）
   4 写 + 4 读 + 2 扫描并发：8000 条记录全部正确
   6 个 goroutine × 4000 次随机操作：1343 个存活 key 全部与 map 一致
```

并发扩展性实测：

| | 单线程 | 并发 |
|---|---|---|
| 写 | 12174 ns/op | **16278 ns/op（更慢）** |
| 读 | 2832 ns/op | **1047 ns/op（快 2.7 倍）** |

**读能随并发扩展，写不能** —— 这是当前架构的准确写照：
读路径靠读锁 + 只读的 SSTable 可以真正并行；
写路径一把大锁串行，并发只带来额外的竞争开销。`group commit` 才是解法（见 DESIGN 第十一节）。

## 十个里程碑做完了

这个项目从"只往文件末尾追加"开始，十步走到一个结构完整的 LSM 引擎。
每一步都是被上一步的问题逼出来的：

```
   ① 追加写            → 写快了，但读要扫全文件
   ② 内存索引          → 读快了，但内存装不下
   ③ 有序文件 SSTable  → 稀疏索引够用了
   ④ MemTable          → 乱序写入怎么产出有序文件
   ⑤ WAL               → 崩溃不丢数据
   ⑥ SSTable 落盘      → 内存和日志不再无限涨
   ⑦ Manifest          → 目录里有什么不算数，登记过的才生效
   ⑧ 多路归并          → 范围扫描
   ⑨ Compaction        → 文件数降下来、垃圾清掉
   ⑩ 分层 + 过滤器     → 读放大压住
   ⑪ 后台执行          → 前台不再等落盘
```

**过程中被测试抓到的真实 bug**（都写在对应的提交信息里）：

| 里程碑 | bug | 为什么隐蔽 |
|---|---|---|
| M2 | 误把分片长度上限当成整条记录的上限 | 只有跨块的大记录才会触发 |
| M3 | flush 后重启数据全查不到 | seq 只从 WAL 恢复，而 WAL 已被删 |
| M4 | 用户 key / 内部 key 混用 panic | 两种 key 长得一样，编译器帮不上忙 |
| M4 | Manifest 泄漏 | 只在 Recover 这条路径上发生 |
| M8 | 布隆过滤器"从没被调用" | 更廉价的边界检查先一步挡掉了探测 key |
| M9 | **锁顺序反转死锁** | 前台 db.mu→bg.mu，后台 bg.mu→db.mu |
| M9 | **迭代器 Close 没加锁导致文件被误删** | race 模式下反而测不出来 |

最后两个尤其值得记：死锁是压测跑到一半卡死才发现的；
文件误删那个**在 `-race` 模式下反而通过了**，只有普通模式的特定时序才触发——
说明 race detector 不是万能的，对拍测试和压测同样不可少。

当前实测：

| 场景 | 耗时 | 吞吐 |
|---|---|---|
| 写入（M1，纯内存） | 546 ns/op | 183 万 ops/s |
| 写入（M2，WAL 不 sync） | 3.8 μs/op | 26 万 ops/s |
| 写入（M2，`SyncWAL: true`） | **2149 μs/op** | **465 ops/s** |
| 读取 | 401 ns/op | 249 万 ops/s |

最后一行是这个项目目前最值得玩味的数字：**开了 fsync 之后慢了 567 倍**。

```
   SyncWAL=false   写完就返回，数据在操作系统的页缓存里
                   → 进程崩溃不丢，【机器断电会丢】

   SyncWAL=true    每次写都等磁盘确认落盘
                   → 断电也不丢，但每次都要等一次真实的磁盘往返
```

这正是 WAL 那一节说的取舍。真实数据库靠 **group commit**（多个并发写攒成一批、
只 fsync 一次）来摊薄这个成本，本项目留到 M9。

## 目标 API

```go
db, err := shale.Open("/tmp/mydb", nil)
defer db.Close()

db.Put([]byte("hello"), []byte("world"))
v, err := db.Get([]byte("hello"))
db.Delete([]byte("hello"))

// 原子批量写
b := shale.NewBatch()
b.Put([]byte("k1"), []byte("v1"))
b.Delete([]byte("k2"))
db.Write(b)

// 范围扫描
it, _ := db.NewIterator()
defer it.Close()
for it.Seek([]byte("user:")); it.Valid(); it.Next() {
    fmt.Println(string(it.Key()), string(it.Value()))
}

// 观察 LSM 的内部状态
fmt.Println(db.Stats())
```

## 两个核心设计

### 内部 key 编码

所有模块存的都不是用户 key，而是**内部 key**：

```
┌──────────────────┬────────────────────────────────┐
│   user key       │  trailer (8 字节)               │
│   任意长度        │  = seq(7字节) << 8 | kind(1字节) │
└──────────────────┴────────────────────────────────┘

排序：先按 user key 升序，相同时按 seq 【降序】
```

`seq` 降序是关键——同一个 key 的**最新版本自动排在最前**，
查找时定位到第一个匹配项就是答案，不用继续扫。

```
("a", 12, 墓碑)   ← Get 定位到这条 → 返回 NotFound ✓
("a",  9, 写入)
("a",  5, 写入)
```

### Batch 的二进制形式就是 WAL 记录

```
┌───────────────┬──────────────┬──────────────────────┐
│ seq (8B, LE)  │ count (4B,LE)│  record × count       │
└───────────────┴──────────────┴──────────────────────┘
```

不需要二次转换：`batch.Bytes()` 直接写进 WAL，恢复时 `batch.Load()` 读回来。
整批共享同一个起始 seq，第 i 条的序号是 `seq+i`——**原子性在 key 编码层面就体现了**。

## 开发

```bash
go test ./...              # 跑全部测试
go test -race ./...        # 竞态检测
go test -bench=. ./...     # 基准测试
go vet ./... && gofmt -l . # 静态检查与格式
```

约束：

- **不引入任何第三方依赖**——依赖越少，越能看清每一层在干什么
- 每个 `internal` 包的注释说明它对应 LSM 原理的哪一步
- 关键取舍在代码里写清楚「为什么」，而不只是「做了什么」
